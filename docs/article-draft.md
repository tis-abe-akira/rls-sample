# PostgreSQL の RLS でマルチテナントを守る実践と、その限界

> 下書き（2026-10-30）。サンプルコード: https://github.com/tis-abe-akira/rls-sample

## はじめに：1行の書き忘れが、他社への情報漏えいになる

複数の顧客企業（テナント）が同じテーブルを共有する SaaS では、すべての SQL に `WHERE tenant_id = ?` を書く必要があります。ただ、人が書く以上、どれだけ気をつけていても次のような書き忘れは起こりえます。

- 一覧画面の SQL で `tenant_id` の条件を書き忘れ、他社の受注が混ざって表示された
- `WHERE id = ?` だけで1件を取得していたため、URL の数字を書き換えると他社のデータが見えた（IDOR）

どちらも「1本の SQL に条件を1つ書き忘れただけ」で起きます。レビューや静的解析で防ごうとすると、守るべき対象が「多数の SQL すべてが、いつも正しいこと」になり、非常に労力がかかります。

そこで PostgreSQL の **Row Level Security（RLS）** を使い、DB 自身に「この接続はどのテナントか」を教えて、そのテナントの行しか返さないようにしました。本記事では、Spring Boot + MyBatis + PostgreSQL で検証した結果をもとに、RLS の効果と、**RLS だけでは守れない部分**をまとめます。

## RLS の基本：DB 側でアクセス制御を強制する

ポリシーを定義すると、PostgreSQL はそのテーブルへのすべてのクエリに条件を暗黙に追加します。

```sql
CREATE FUNCTION current_tenant_id() RETURNS bigint LANGUAGE sql STABLE AS $$
  SELECT NULLIF(current_setting('app.tenant_id', true), '')::bigint
$$;

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE  ROW LEVEL SECURITY;   -- テーブル所有者にも適用する

CREATE POLICY tenant_isolation ON orders AS RESTRICTIVE
  USING      (tenant_id = current_tenant_id())   -- 見える行（SELECT/UPDATE/DELETE）
  WITH CHECK (tenant_id = current_tenant_id());  -- 書き込める行（INSERT/UPDATE）
```

これで `SELECT * FROM orders` も `WHERE id = 3` も、DB の中では自社の行だけに絞られます。他社の行への UPDATE / DELETE は 0 件になり、他社の `tenant_id` での INSERT はエラーになります。

テナントが設定されていなければ `tenant_id = NULL` となって **0 件** になります。設定を忘れたときに「全部見える」ではなく「何も見えない」側に倒れる（fail-closed）のが重要な性質です。なお `NULLIF(..., '')` は必須です。一度 `SET LOCAL` した接続では、トランザクション終了後に `current_setting` が空文字を返すようになり、`''::bigint` がエラーになるためです。

## アプリケーションから DB にテナントを届ける

アプリケーション側では、Spring の `JdbcTransactionManager#prepareTransactionalConnection`（BEGIN 直後に同じ接続で呼ばれるフック）で、次の SQL を発行しています。

```sql
SELECT set_config('app.tenant_id', '1', true);   -- 第3引数 true = SET LOCAL
```

ポイントは **`SET LOCAL`（トランザクション単位）を使うこと** です。セッション単位の `SET` を使うと、コネクションプールで接続が再利用されたときに、次のリクエストが**前の人のテナント**で動いてしまいます。同様に、テナントを保持する ThreadLocal も try/finally で必ず片付けます（Tomcat のスレッドも使い回されるため）。

## RLS だけでは守れないもの

ここまでで、SQL の書き忘れは RLS で防げるようになりました。ただし、RLS が守れる範囲には限りがあります。

> **RLS が守るのは「SQL の書き間違い」までです。「誰として動いているか」の間違いは守れません。**

DB は渡されたテナント ID を忠実に使うだけです。ID が偽物なら、偽物のテナントのデータを**正しく絞り込んで**返してしまいます。守りは「テナントが決まって、DB に届くまで」の鎖になっていて、どこか1か所が切れると抜け道になります。

### 1. テナント ID は、サーバーサイドの信頼できる情報から取る（最重要）

最も影響が大きく、RLS では絶対に防げない穴です。

- ❌ リクエストヘッダ（`X-Tenant-Id`）、クエリパラメータ、リクエストボディの `companyId` をそのまま信用する。書き換えるだけで誰でも他社になれます
- ✅ 署名を検証した JWT のクレームや、サーバー側のセッションから取る
- ✅ 複数テナントに所属するユーザーのために「どのテナントで操作するか」をヘッダで選ばせる場合も、**認証情報の所属テナントに含まれているかを必ずサーバー側で突き合わせる**。含まれていなければ 403 を返し、なりすましの試みとしてログに残す
- ✅ リクエストボディに `tenant_id` を含めない。登録時のテナントもサーバー側で決める

サンプルでは、JWT の `tenant_ids` クレーム（所属テナントの一覧）を根拠にしています。この方式は、IdP がクレームに正しい所属テナントを入れていることが前提です。そのため、IdP 側でテナントの割り当てを管理する手順（入社・異動・退職のときにクレームの値をどう更新するか）もあわせて決めておきます。さらにサンプルでは、そのテナントの users テーブルに本人が登録されていることも確認しています。万一クレームに誤ったテナントが入っても、そのテナントに登録のないユーザーは 403 で弾けます。

### 2. 子テーブルにも tenant_id を持たせ、親とのずれを DB で防ぐ

「明細は親の受注を経由してしか読まないから、明細テーブルに `tenant_id` は要らない」という判断は危険です。子テーブルを直接 SELECT する SQL が1本でもあれば、全テナントの明細が見えます。

```sql
CREATE TABLE order_details (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,                       -- 子にも tenant_id を持たせて RLS をかける
  order_id  bigint NOT NULL,
  ...
  FOREIGN KEY (tenant_id, order_id) REFERENCES orders (tenant_id, id)   -- 複合外部キー
);
```

- **子テーブルにも `tenant_id` を持たせ、同じ RLS ポリシーをかける**
- **外部キーを `(tenant_id, 親の id)` の複合にする**。「A社の受注に B社の明細がぶら下がる」「A社の受注に B社のユーザーが紐づく」といった、テナントをまたぐ関連を DB が作らせません。外部キーのチェックは RLS を無視して行われるので、ここは RLS ではなく制約で守るのが確実です
- 親テーブル側には `UNIQUE (tenant_id, id)` を追加しておく（複合外部キーの参照先）

### 3. RLS が効くロールで接続する

スーパーユーザー、`BYPASSRLS` 属性を持つロール、`FORCE` が付いていないテーブルの所有者は、ポリシーを素通りします。DDL 用（所有者）、アプリケーション用（RLS が効く）、バッチ・運用用（BYPASSRLS）とロールを分け、アプリケーションは必ず RLS が効くロールで接続します。Spring Boot の Docker Compose 連携はスーパーユーザーで接続するので注意が必要です。

### 4. トランザクションの途中でテナントを切り替えない

DB へのテナント設定は BEGIN のときに1回だけです。トランザクションの中で Java 側のテナントだけを切り替えると、Java は B社、DB は A社のまま動きます。監査ログの宛先やキャッシュのキーに誤ったテナントが使われる原因になるため、サンプルではトランザクション実行中の切り替えを例外にしています。全テナントを順に処理するバッチは「テナントごとに切り替え → その内側でトランザクション」の順に書きます。

### 5. SQL インジェクションがあれば、テナントを切り替えられる

`app.tenant_id` のようなカスタム設定値は、どのロールでも自由に書き換えられます。SQL インジェクションがあると、攻撃者は同じトランザクションの中で `set_config('app.tenant_id', '2', true)` を実行して他社に切り替えられます（実際に検証で再現しました）。**RLS はインジェクション対策の代わりになりません。** MyBatis なら `${}` を禁止し `#{}` だけを使います。

### 6. RLS を迂回する DB オブジェクトに注意する

- **ビュー**は、デフォルトでは**ビューの所有者**の権限でテーブルを読みます。所有者がスーパーユーザーなら、テナントを設定していても全社の行が返ります（検証で再現）。PostgreSQL 15 以降は `WITH (security_invoker = true)` を付けます
- `SECURITY DEFINER` の関数、マテリアライズドビュー（スナップショットにポリシーが効かない）も同様です

### 7. そもそも RLS の守備範囲の外にあるもの

アプリケーションのキャッシュ（id だけをキーにした `@Cacheable`、MyBatis の2次キャッシュ）、S3 などのファイル、全文検索エンジン、外部 API は DB を通らないので守れません。キャッシュのキーには必ずテナントを含めます。

## テナントの中の権限：RESTRICTIVE と PERMISSIVE

「一般ユーザーは自分のデータだけ、管理者はテナント内の全データ」という要件も RLS で表現できます。ポイントは、ポリシーを2段に分けることです。

```sql
-- テナントの壁: RESTRICTIVE（すべてのポリシーに AND で効く）
CREATE POLICY tenant_isolation ON orders AS RESTRICTIVE USING (tenant_id = current_tenant_id()) ...;
-- テナントの中の権限: PERMISSIVE（OR で効く）
CREATE POLICY owner_or_admin ON orders USING (user_id = current_app_user_id() OR current_app_is_admin()) ...;
```

テナントの壁を PERMISSIVE で書くと、後から誰かが「監査担当は全部見える」というポリシーをテナント条件なしで追加したときに、OR で効いて**全テナント**が見えてしまいます。RESTRICTIVE にしておけば、どんなポリシーを足してもテナントの壁が AND で掛かります。

## 組織階層は「判断はアプリケーション、強制は DB」

さらに「部長は部員の、事業部長は事業部全体のデータを見られる」という要件を検討しました。この程度なら RLS だけでも書けますが、今後「兼務」「代理」「休暇中だけの権限」が増えると、ポリシーが複雑になり、変更のたびに DDL が必要になります。一方、判定をアプリケーションに全部移すと、テナントの中で WHERE を書き忘れたときに守れなくなります。

そこで、**見える範囲の判断はアプリケーションで行い、結果だけを DB に渡して RLS が強制する**形にしました。

1. アプリケーションが組織階層から「見てよい部署の一覧」を算出する（部長なら `{第一営業部}`）
2. その一覧を `set_config('app.visible_org_ids', '{2}', true)` で DB に渡す
3. RLS は `org_id = ANY(current_app_visible_org_ids())` で「渡された一覧に入っているか」だけを見る

兼務や代理が増えても変わるのは 1 の算出ロジックだけで、RLS のポリシーは変わりません。認可を受注1件ずつではなく「部署の単位」で行うので、一覧の絞り込みも軽く済みます。算出部分はインターフェースとして切り出してあるので、要件が複雑になったときには、OpenFGA（Google Zanzibar 型の認可サーバー、CNCF Incubating）などへの置き換えも選択肢になり得ます。

## 導入チェックリスト

- [ ] テナント ID は認証情報（JWT のクレーム、サーバー側のセッション）から取り、ヘッダやボディの値をそのまま信用していない
- [ ] テナントを選ばせる場合、所属テナントとの突き合わせをサーバー側で行っている
- [ ] 子テーブルにも `tenant_id` と RLS があり、外部キーは `(tenant_id, 親の id)` の複合になっている
- [ ] アプリケーションは RLS が効くロールで接続し、テナント所有テーブルすべてに `ENABLE` + `FORCE` + ポリシーがある
- [ ] テナントの壁は `AS RESTRICTIVE` で書いている
- [ ] テナント設定は `SET LOCAL`（`set_config(..., true)`）で、トランザクション開始時の1か所だけで行っている
- [ ] `${}` などの文字列連結による SQL がない
- [ ] ビューに `security_invoker = true` が付いている。`SECURITY DEFINER` の関数を把握している
- [ ] キャッシュのキーにテナントが含まれている
- [ ] テストデータは2テナント以上あり、「他社のデータが見えない・消せない・作れない」ことをテストしている
- [ ] RLS が無効なテーブルや `security_invoker` のないビューを検出する SQL を CI で実行している

## まとめ

RLS があっても、アプリケーション側の `WHERE tenant_id = ?` は消さずに残すことを推奨します（多層防御）。RLS は「書き忘れたときの安全網」であって、「書かなくてよくする仕組み」ではありません。

RLS の本当の価値は、守るべき場所を「すべての SQL」から「少数の制御点」に絞れることです。制御点とは、テナントの決定、伝播、接続への設定、DB の設定の4つです。ここを重点的にレビューし、残りは CI の機械的なチェックで守ります。人が多数の SQL を見張り続けるより、ずっと確実な方法です。ただしその前提として、**テナント ID そのものが正しいこと**だけは、RLS ではなく私たちが保証しなければなりません。
